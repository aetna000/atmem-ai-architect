# AtMem infrastructure and cost review gate

## Owner clarification: one Architect product, a Spec Kit IDE

The native product experience takes precedence over the initial standalone
distribution plan. The reviewer is an internal engine used by AtMem AI Architect;
CLI/MCP are adapters for coding agents, not a separate product users must install.

The owner describes one continuous journey:

> Give Architect a Word document, an existing codebase or a couple of prompts;
> develop the Spec Kit, system/subsystem design, infrastructure rules and budget;
> press Code it; watch Codex or Claude implement, test and validate the system
> live in the same UI; ask AtMem in chat where the project stands.

Requirements established by the owner on 2026-11-18:

1. The user lives in Architect. Requirements, functional specifications, system
   design, infrastructure, budget, code, validation and delivery are views of the
   same versioned project, not independent workflows requiring manual copying.
2. Approved rules and binding history are retained in real AtMem memory. A local
   architecture.md is an interoperability/export option, not the native UI store.
3. The UI exposes coding-agent progress, actions, changed files, specification/task
   status and independently recorded tests and rule checks. Hidden terminal work
   is not an adequate native experience.
4. Bidirectional binding means changes propagate invalidation and reconciliation
   in either direction, like derived views of React application state. A code
   change must not silently rewrite an approved requirement to agree with itself.
5. Every accepted code change links to approved specification/task IDs. A
   contradiction, missing binding or stale evidence blocks readiness. File
   presence and an agent saying "done" do not establish implementation or tests.
6. Bind specification revision, task, subsystem, worktree/base commit, changed
   files, artifact digest, test execution and policy revision. Preserve the
   history in AtMem. Editing any input invalidates dependent evidence.
7. Multiple agents/worktrees must reconcile against the same project/specification
   identities. Conflicting changes remain visible; no silent merge or duplicate
   completion. The owner's 100-agent example is a scalability requirement, not a
   claim that the current four-session local worker supports 100 concurrent jobs.
8. Chat answers project-status questions from these bindings and actual evidence,
   distinguishes recorded/stale/current, and does not infer readiness from prose.
9. Browser acceptance exercises the actual backend and AtMem SDK, including
   policy violations, failed checks, concurrent/stale responses and project scope.

The detailed statuses in progress.json distinguish implemented native slices
from the remaining IDE/binding work. No overall IDE completion is claimed merely
because the standalone reviewer and a live Spec Kit hook work.

## Original reviewer scope

Owner-directed implementation of `atmem-review-hook/PLAN.md`, on a new branch from main. The supplied scaffold is design evidence; its claimed prior validations are not current execution evidence.

The product reviews supplied plan text and optional Terraform show JSON against a separate architecture policy. It returns pass/warn/fail, exact evidence, suggested fixes and explicit unknowns. It never generates/runs Terraform, reads arbitrary client paths, edits customer files or calls cloud-provider APIs. Caller artifact paths are citation labels only.

1. Deterministic checks cover structured attribute predicates, provider regions, service restrictions and public ingress. Unknown/computed/deferred values, missing scope or unsupported rules cannot earn a pass.
2. Budget checks require a real attributable cost-engine result in the matching currency and environment. Missing/partial pricing is unverified; illustrative sample costs are never measured evidence.
3. Prose/ADR interpretation is a separately enabled model adapter. No source leaves the reviewer by default. Model findings require exact validated citations; source text cannot grant permissions or override policy.
4. Expiring exceptions retain the original violation and accepted exception identity. No silent suppression.
5. MCP stdio exposes only review_plan with input/output validation and bounded payloads. A local CLI provides machine JSON and CI exit codes; no private artifact persistence by the reviewer.
6. Spec Kit/OpenSpec integrations consume actual review output and document prompt/file-existence enforcement limits. A CI command must reject failed, stale or missing review evidence.
7. Deliver a runnable local package, before/after demo generated by the actual engine, tested installation instructions and exact coverage limits. Publishing, catalog submissions, hosted execution, paid model calls and a live pricing credential run remain separately authorized or access-dependent.

No revenue or adoption is established by this implementation. The commercial entry point is infra/cost-policy enforcement inside existing agent workflows; hosted team policies, usage/billing and commercial rollout follow demonstrated local behavior.
