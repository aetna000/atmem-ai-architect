# Retain implementation requests through setup and recovery

The owner wants a guided Design → implementation → tests → results journey. Inspection found two dropped-request paths: the entry action opened model setup before storing the request, and the implementation panel consumed requests before checking whether it could submit them. An uncertain prior session could discard a new request; a failed history lookup could allow new work without confirming earlier work.

The entry now records the project-scoped request and opens its outcome workspace. The panel retains it while a model/effort is selected, design changes settle, or an uncertain existing session is recovered. It consumes the request only once the local submission operation can start; the existing action lock prevents duplicate submissions. It explains the wait and allows cancellation. A failed earlier-work lookup now blocks submission and offers an explicit retry; no inferred empty history on a transient failure. Existing sessions retain their own model and effort. This applies across domains/providers, not to a named evaluation case.

Five real-browser fixture scenarios pass on source and live5285: missing exact selection → choose model → one create/start; busy design → wait → one create/start; failed history lookup → explicit retry → one create/start; starting session → explicit recovery → one start on the same session/no create; cancellation → setup completion sends no start. Check the complete preserved implementation-and-tests intent, context SHA, exact model/effort, callback count and zero browser errors. All backend responses are synthetic: no native generation, no cloud and no owner project writes.

The existing broader engineering browser suite also passes: save-before-submit/context recheck, failed save draft preservation, transcript, retained steering, reload/recovery without replay, immutable download, validation history and desktop/mobile. 555 JS tests and production build pass (existing bundle-size warning). Receipts are attached.
