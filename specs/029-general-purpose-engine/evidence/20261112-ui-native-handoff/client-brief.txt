Create a local-first rehearsal-room booking application for a small community arts centre. This is an exposed UI/receiving diagnostic, not one of the original28 workloads or a cloud acceptance test.

Accepted scope: one trusted desk operator on one local workstation, a browser UI and a Node HTTP backend with durable local storage. Bind the application to loopback by default. No cloud provider, cloud account, deployment, external service, sign-in or payment is requested; explain that opening it to other machines requires a separately reviewed security/deployment design. Do not invent a cloud resource or credentials. Keep the implementation portable to another engineer's machine and preserve the full specification below.

R1: The operator can list bookings and create a booking with room (Studio A or Studio B), a real Gregorian calendar date in YYYY-MM-DD format, slot AM or PM, and member display name of 1 through120 Unicode code points after trimming. Display names may contain non-BMP characters and punctuation. Do not replace the bound with UTF16 length. Return helpful validation errors and preserve entered form data when a request fails.
R2: There can be at most one active booking for each room/date/slot. Concurrent competing creates must yield exactly one active booking, with the other rejected clearly; no silent overwrite. Use an explicit request identifier for create idempotency: an exact retry returns the original booking, and reusing that identifier for different input is rejected. Keep cancelled records for the operator's history.
R3: The operator can cancel an active booking and then book its freed slot again. A repeated cancellation is harmless. Booking identity and historical member text remain intact. List/filter active versus cancelled clearly; no ambiguity between a cancelled historical record and an available slot.
R4: Committed create and cancel changes survive application process replacement with the same data directory. Interrupted/invalid data must not silently reset the registry or masquerade as an empty successful database. Document the storage consistency model, backup/restore and supported single-process ownership; do not claim multi-node support.
R5: Browser UI works with real local HTTP, not only route stubs. Inputs and returned values render safely as text; invalid data, server errors, conflict, immediate interaction during initialization and reload have clear recovery without losing user intent or creating duplicates. State the actual privacy boundary; no external network request is needed.
R6: Include unit/HTTP and actual browser tests for all these behaviors, positive and negative, including leap-day invalidity,120 versus121 non-BMP code points, double-booking concurrency, same/different idempotency retries, cancellation/rebooking, process restart, corruption and inert markup text. Run applicable registered local checks on captured files, read full reports and repair at source. Skipped/unexecuted checks remain explicit.
R7: Deliver the complete source, exact runtime/dependency declarations, requirements/architecture/interfaces, acceptance traceability, dependent implementation tasks and evidence, clean receiving build/test/run instructions plus backup/restore/rollback. A standard Spec Kit feature directory is acceptable. Receiving instructions must not require private worker paths. Optional browser test tooling may use the explicitly supplied operator Playwright module during these checks, but document a pinned portable receiving setup. Do not install from the network or replace actual application work with a design document.
