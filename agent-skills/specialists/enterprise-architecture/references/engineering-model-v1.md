# AtMem engineering model v1 authoring contract

This is an implemented AtMem interchange grammar, not full UML conformance. Include a complete `engineeringModel` object in `architecture.canvas.json` for detailed class/data modeling. The host validates references against the combined existing/new blocks and requirements before applying the proposal. Omission preserves an existing model. Null cannot clear it. Preserve model and semantic IDs, existing ownership, members and relationships. Accepted elements cannot be rewritten through generation. Generated elements cannot claim `accepted` status. Record proposed consequential changes in the authored review instead.

## Root and identities

Root fields: `format: "atmem.engineering-model"`, `version: 1`, `id`, `name`, `elements: []`, `relationships: []`, `diagrams: []`. No other root fields. IDs are globally unique across elements, members, relationships, indexes, checks and diagrams. Use stable semantic IDs, not names. All member `typeRef` values reference actual classifier IDs, including primitive logical data types explicitly declared as `dataType` elements. No programming language or database engine is required.

Element required fields: `id`, `name`, `kind`, `basis`. Kinds: `package`, `class`, `interface`, `dataType`, `enumeration`, `entity`, `table`. Basis: `source` for source-supported design content, `proposed` for derived engineering choices; `accepted` is reserved for already accepted elements. Optional common fields: `ownerId` (another element, no cycles), `blockId` (architecture block ID), `description`, `requirementIds` (existing/new requirement IDs). Assign implementation-bearing classes and entities to responsible modules. Describe responsibilities and source traceability. Classifiers are class/interface/dataType/enumeration.

## Classifiers

Classifier optional fields: `attributes`, `operations`, `invariants` (text array). Enumeration alone also allows `literals` (unique text array).

Attribute fields: required `id`, `name`, `typeRef`; optional `visibility` (public/protected/private/package), `multiplicity: {lower: 0, upper: "*"}` (nonnegative bounds; upper may be integer), `readOnly` (boolean), `defaultValue` (text), `description`. Nullability on attributes is optional; use multiplicity for logical cardinality.

Operation fields: required `id`, `name`, `parameters` (array); optional `visibility`, `description`, `preconditions`, `postconditions`, `raises` (classifier ID array). Preconditions/postconditions are text arrays. Each parameter has required `id`, `name`, `typeRef`, `direction` (in/out/inout/return), plus optional attribute properties except nullable. At most one return parameter. Describe observable rejection and durable effects, not implementation code. Use a declared logical result/error classifier where needed.

## Logical data and optional physical mapping

Entity/table optional fields: `columns`, `primaryKey`, `indexes`, `checks`, `physicalMapping`. A column has required `id`, `name`, `typeRef`, `nullable` (boolean), optional `defaultValue` and `description`. Visibility, readOnly and multiplicity do not apply to storage columns.

`primaryKey` is an ordered array of owned nonnullable column IDs. Index: `{id,name,columns:[ownedColumnId],unique:boolean,purpose}`. Preserve composite column order. Check: `{id,name,expression,language}`; mark natural-language constraints as such, not executable SQL. Explain the queries served by indexes and the invariants served by constraints.

Optional `physicalMapping`: `{technology,name,columnTypes:{columnId:physicalType},namespace?}`. Keep this separate from logical types. Do not select a database or language merely to populate the model. A partial mapping is not a migration, executable DDL or completeness proof.

## Relationships

Required fields: `id`, `name`, `kind`, `source`, `target` (element IDs). Optional `description`, `sourceEnd`, `targetEnd`. Kinds: association/aggregation/composition/generalization/realization/dependency/foreignKey/mapping. Ends allow `role`, `multiplicity`, `navigable` (boolean). Generalization is child to parent and must be acyclic. Realization targets an interface. Mapping connects classifier to entity/table. Explain mapping responsibilities in the description. Other relationship kinds do not establish runtime connectivity or implementation evidence.

Foreign keys require ordered `sourceColumns`, `targetColumns` arrays of equal nonzero length, columns owned by their respective endpoints, compatible logical type IDs and an exact ordered target primary/unique key. Optional `onDelete`, `onUpdate`: restrict/noAction/cascade/setNull/setDefault. setNull requires nullable source columns. Do not invent a referential action where the source does not settle the trade-off; propose and justify it. Column-level SQL constraints and dialect-specific behavior require later lowering and tests.

## Views, readability and limits

Diagram fields: required `id`, `name`, `kind` (class/schema), `placements`, `relationships` (relationship ID array); optional `scopeId` (element ID). Placement: `{elementId,x,y,detail?}`; detail is summary/full. Coordinates finite within ±1,000,000. Class views contain classifiers; schema views contain entities/tables. Every listed relationship must have both endpoints placed in the view. Reuse element IDs across views; do not create a copied class for each diagram. Use focused views and whitespace for readable compartments. The initial renderer uses 350-unit-wide cards with dynamic height; avoid overlapping placements. Complex routing, ports and other diagram grammars are unfinished.

Bounds: 2000 elements, 4000 relationships, 500 diagrams, 300 placements per view, 1000 relationship references per view. Per element: 200 attributes/operations, 300 columns, 100 indexes/checks; per operation: 100 parameters. Text/identity limits apply: IDs 100 Unicode points, names 200, descriptions 4000. The generated canvas proposal must fit its 2 MB capture contract. These are receiving limits, not a scale qualification. Never discard requirements to fit them; retain complete authored evidence and disclose any projection gap.

## Architecture quality and handoff

Derive the model from responsibilities and source requirements, not a fixed domain template or a diagram count. Specify state, authority, invariants, operation inputs/results, persistence identity and failure semantics. Separate source facts from proposed internals. The module kit exports the full shared model once and assigns explicit element IDs per module; adjacent elements remain context. Reconcile these elements with interface descriptions, tasks and acceptance cases in the authored documents. Structural validity alone does not demonstrate architectural completeness or executable agent readiness. Behavior fragments, ports, deployment semantics and automatic code generation are not supported by this v1 grammar; use the existing authored specifications and explicitly retain those modeling gaps.

## Per-module verification cases

In each block's `buildSpec`, supplement the prose `tests` with `verificationCases`. Each case has required fields `id`, `name`, `category` (unit/contract/integration/security/recovery/load/acceptance), `requirementIds` (1–50 unique source requirement IDs), `environment`, `setup`, `input`, `action`, `expected`, `evidence`. The last six are complete text fields, each up to 4000 Unicode points. Specify concrete starting state and input values, an action or failure/concurrency schedule, observable success/denial/state outcomes and the exact evidence the implementer must capture. Do not invent performance targets. Express unresolved contractual thresholds as explicit gates while providing the workload and measurement procedure.

Optional `interfaceId` must name an incident architecture interface. Optional `operationId` must name an operation whose owning element is assigned to this block. IDs must resolve against the complete proposal. Case IDs are unique within the module, 1–100 Unicode points; names are 1–150. At most 100 cases per module. Omission preserves existing cases during section merging; replacement retains their identities. These are test specifications: do not include status/pass flags, fabricated logs or execution claims. The exported verification-cases.json always states execution not_run. Actual outcomes must later bind to the exact implementation artifact and environment through evidence records. Do not reuse a generic test list across unrelated modules.

## Connecting behavior to operations

Scenario steps in block buildSpec scenarios and systemSpec journeys may carry `operationId`, referencing an operation in the shared engineering model. Commands, queries and event handlers reference the receiving module's operation; results reference that same operation on their sending module. Always declare messageKind and the relevant participant block IDs so ownership can be checked. Do not attach an operation to an arbitrary event merely to make a count pass. Omit unresolved links and record the missing modeling work; labels are not reference identities. Existing unbound calls to modeled receivers remain review items. Unknown IDs or contradictory ownership are errors and block structural acceptance. Per-module scenario documents retain these IDs, and the module diagram view can navigate from a linked step to its owning class and signature. This reference alone does not model interaction fragments, operation arguments, return-value correspondence, precondition execution or runtime behavior.

## Responsibility and contract coherence review

For implementation-bearing elements assigned to blocks, provide a responsibility description that makes ownership and effects clear. Reconcile operation preconditions, caller/authorization context, request/replay identity, returned outcomes, nullability and collection cardinality with the module's interfaces and logical records. Context can be explicit parameters or an explicitly documented bound execution context; do not trust caller-supplied identity merely because it appears in a signature. If one command changes multiple records, define whether the result contains a collection or a primary result with typed traversable lineage. Do not let prose promise multiple results while the only modeled outcome has an unexplained scalar. Keep source facts distinct from proposed internal decisions. Missing vendor/business facts remain qualification gates; missing engine detail is elaboration work, not an owner question.

During refinement, read the current modeling-grammar reference with its returned digest and pagination when tools are supplied. The original workspace resource is creation-pinned and may precede later engine capabilities; do not modify it or its receipt. Current tool reads provide their own resource hashes. Retain existing semantic IDs, ownership, source requirements and accepted records while adding detail.

## Logical system diagrams

Provide a separate `systemModel` object in `architecture.canvas.json`. AtMem lays out these views. Coordinates and Mermaid are unnecessary for native views. Reuse semantic IDs between diagrams and across refinements. This contract models logical design and currently supports static flows and ordered scenarios.

- Root required fields: `format: "atmem.system-model"`, `version: 1`, `id`, `elements`, `exchanges`, `diagrams`. Use unique, stable model IDs of 1–100 characters. Start with a letter or digit and use letters, digits, underscores or hyphens.
- Every element and exchange needs `id`, `kind`, `name`, `description`, `basis`, `requirementIds`. Names are at most 150 characters and descriptions at most 2000. Basis is `source` with at least one linked requirement or `proposed` with known traces where applicable. References use exact current/new requirement IDs.
- Element kinds: `actor`, `component`, `function`, `functionPort`, `componentPort`. A component may set `blockId` to its implementation block. Components and functions may each set `parentId` to another element of their own kind. A function may set `allocatedTo` to the responsible component or actor. Ports require `ownerId` and `direction` (`in`, `out`, `inout`). Component ports belong to a component or actor, function ports to a function.
- Exchange kinds: `functional` or `component`. Both require `source` and `target`, respectively an output-capable and input-capable port of the matching kind on different owners. Include `items`, a nonempty array of up to 30 distinct payload/data names of up to 150 characters. A component exchange may set `interfaceId` to the corresponding directed board edge when both endpoints are allocated to those blocks. A functional exchange may set `componentExchangeId` to its carrying component exchange, whose port owners must match the two function allocations.
- A diagram requires `id`, `kind`, `name`, `elementIds`, `exchangeIds`. Kind `components` shows components/actors and component exchanges. Kind `functions` shows functions and functional exchanges. Kind `sequence` has components/actors as ordered lifelines and component exchange IDs in send order. The same exchange may occur more than once in a sequence. Include both endpoint owners in each diagram that shows an exchange. Include at least one view of each kind. Derive separate focused normal and failure sequences where the brief supports them.
- Bounds: 800 elements, 1200 exchanges, 120 diagrams, 50 requirement references per record, 40 nodes and 100 exchanges per static view, 12 lifelines and 60 messages per sequence. Keep a compact logical overview. Split dense views by responsibility and scenario, ideally with 4–8 visible elements, and reuse the same IDs. Give arrows a concise label and keep protocol detail in the exchange description and contract. Avoid orphaned child symbols in an overview; include them in a focused view with their relevant exchanges.
- Prefer a complete trace from a requirement through a function and its allocation, through a typed exchange and scenario, into the module spec and verification cases. Explain uncertain external behavior and validation limits in the review. Keep existing authored diagrams for states, physical placement and behaviors outside this grammar.
